[viz] Don't release presented overlays on failed swaps

IN REVIEW2026viz
2026. 9. 24.Indigochi1d
https://crrev.com/c/8448731

Chromium viz 계층에서 swap이 실패했을 때, 여전히 화면에 표시 중인 오버레이의 접근 권한이 파괴되던 버그를 수정했다. DoFinishSwapBuffers()가 swap 결과를 인자로 받으면서도 읽지 않고 이전 프레임의 오버레이를 무조건 해제하던 것이 원인이었기에 해제 대상을 결정하는 시점을 제출(Present())에서 완료(DoFinishSwapBuffers())로 옮겨 해결했다.

문제 설명

  1. 오버레이는 하드웨어에 제출된 뒤에도 다음 프레임이 덮어쓸 때까지 계속 화면에 표시된다. 그래서 해제를 한 프레임 미뤄야 하고, SkiaOutputDeviceBufferQueue는 이를 참조 카운트로 관리한다.
  2. Unref()는 카운트를 하나 줄이는 것에서 끝나지 않고 representation과 scoped read access를 파괴한다.

원인

Present()가 해제 대상 목록을 완료 콜백에 바인딩한다. base::BindOnce는 인자를 자기 내부 필드로 이동시켜 보관하므로 이 시점에 해제 대상이 고정된다. 그래서 DoFinishSwapBuffers()는 result.swap_result를 인자로 받고도 읽지 않았다. 읽어봐야 바꿀 수 없었기 때문이다.

쉽게 생각했을 때 if문 하나를 추가하는 것으로 해결하고자 하였으나 해결되지 않았다. 실패했을 때 해제해야 하는 것은 이번 프레임의 목록인데 그 목록은 다음 콜백에 바인딩될 예정이라 이 함수에서는 접근할 수 없었다.

증상

swap이 실패하면 그 프레임은 화면에 표시되지 못하므로 이전 프레임이 그대로 표시되고 있다. 그런데 코드는 바로 그 이전 프레임을 파괴한다. 반대로 화면에 표시된 적 없는 오버레이는 한 프레임 더 유지하고 있다.

해결 내용

1. 겹친 의미를 가진 변수를 분리

committed_overlay_mailboxes_ 하나가 제출됨과 표시 중을 같이 뜻하고 있었다. swap이 성공하는 동안에는 두 의미가 같지만 실패하면 달라지는데, 변수가 하나뿐이라 그 상태를 표현할 수 없었다.
따라서 pending, submitted, presented 세 단계로 나눴다. 중간 단계는 circular_deque로 두어 부모 클래스의 SkiaOutputDevice::pending_swaps_와 같은 순서로 꺼낸다.

2. 결정을 완료 시점으로 이동

// Present() — 결정하지 않고 큐에 적재만
submitted_overlay_mailboxes_.push_back(std::move(pending_overlay_mailboxes_));
pending_overlay_mailboxes_.clear();

// DoFinishSwapBuffers() — 결과를 아는 지금 판단
if (result.swap_result == gfx::SwapResult::SWAP_ACK) {
  replaced = std::exchange(presented_overlay_mailboxes_, std::move(swapped));
} else {
  replaced = std::move(swapped);  // 화면은 그대로, 못 뜬 이번 것을 해제
}

SWAP_ACK만 성공으로 보는 화이트리스트를 택했다.
SWAP_NAK_RECREATE_BUFFERS는 HardwareDisplayController와 DrmWindow 양쪽에서 page flip을 커밋하기 전에 반환하고 swap_result.h는 SWAP_SKIPPED를 SWAP_FAILED처럼 다루라고 적어두었다.

테스트 방법

  1. 회귀 테스트 ScheduleOverlaysSwapFailed를 추가했다. <Figure 3>의 three-frame 시나리오를 그대로 코드로 옮겼다.
    또한, 기존 MockPresenter::SwapComplete()가 SWAP_ACK을 하드코딩하고 있어서 실패한 swap을 흉내낼 수 없었고, 결과를 인자로 받도록 고쳤다.

  2. 테스트가 실제로 버그를 잡는지 역으로 확인했다. 수정 로직만 임시로 되돌리자 정확히 세 지점에서 실패했다.

HasOverlay(A) → false   ← 화면에 떠 있는데 파괴됨
HasOverlay(B) → true    ← 못 뜬 건데 살아있음
  1. viz_unittests 2,424개가 전부 통과한다.

실제 SWAP_FAILED는 주로 ChromeOS DRM 경로에서 발생하기 때문에 로컬 macOS 테스트로는 검증되지 않는다. CQ의 ChromeOS 빌더를 확인해야 했고 26.09.25일자로 CQ Dry Run이 pass 됨을 확인했다.

배운 점

  • 표면적으로는 if문이 빠진 것처럼 보이지만, 실제로는 결정을 내리는 시점이 정보가 도착하는 시점보다 앞서 있는 구조 문제였다(<Figure 5>). 이런 경우에는 분기를 추가하려 해도 한쪽 가지에 넣을 데이터가 존재하지 않는다.
  • 이름 하나가 두 의미를 겸하면 표현할 수 없는 상태가 생긴다. 변수를 나눈 것이 리팩터링이 아니라 수정의 일부였던 이유다.
  • SkiaOutputSurfaceImplOnGpu::PostSubmit()의 skip 경로는 Present()를 거치지 않아 pending_overlay_mailboxes_가 비워지지 않는다. Reshape()의 DCHECK가 실패할 수 있어 별도 이슈로 낼 만하다.
