1a:T41b0,<p>POSIX 환경의 Chromium에서 File System Access API의<br /><code>showSaveFilePicker()</code>로 새 로컬 파일을 만들 때 고정된 <code>0600</code> 권한 대신<br />프로세스의 umask를 반영하도록 개선했습니다. 기존 파일의 권한은 그대로<br />유지하고, 심볼릭 링크나 FIFO 같은 비정규 파일을 안전하게 거부하도록 파일<br />생성·초기화 경로도 함께 강화했습니다.</p>
<h2 id="문제-설명">문제 설명</h2><p><a href="https://wicg.github.io/file-system-access/#api-showsavefilepicker">File System Access API 명세</a>에<br />따르면 <code>showSaveFilePicker()</code>는 사용자가 선택한 파일이 존재하지 않으면 빈<br />파일을 생성하고, 이미 존재하면 내용을 비운 뒤 파일 핸들을 반환해야 합니다.</p>
<p>기존 Chromium 구현은 이 동작을 storage backend의<br /><code>CreateAndTruncateFile()</code>을 통해 처리했습니다. 이 경로에서 POSIX 로컬 파일을<br />새로 만들면 권한이 <code>0600</code>으로 고정되어 프로세스의 umask가 반영되지<br />않았습니다.</p>
<p>예를 들어 사용자의 umask가 <code>0002</code>라면 일반적인 저장 경로에서는 다음과 같은<br />권한을 기대할 수 있습니다.</p>
<pre><code class="hljs language-text">기본 생성 모드: 0666
umask:          0002
최종 권한:      0664</code></pre><p>하지만 기존 <code>showSaveFilePicker()</code> 경로에서는 항상 <code>0600</code>으로 생성되었습니다.<br />소유자만 파일을 읽고 쓸 수 있기 때문에 보안상 지나치게 느슨한 문제는<br />아니었지만, 사용자가 설정한 그룹 공유 정책과 다른 브라우저 저장 경로의<br />동작을 따르지 않는 일관성 문제가 있었습니다.</p>
<p>단순히 파일 생성 모드를 변경하는 것만으로는 충분하지 않았습니다.</p>
<ul>
<li>새 파일은 <code>0666</code>을 기본 모드로 사용하면서 프로세스 umask를 적용해야 합니다.</li>
<li>기존 파일을 비울 때는 기존 접근 권한을 변경하지 않아야 합니다.</li>
<li>사용자가 선택한 경로가 심볼릭 링크라면 링크 대상 파일이 의도치 않게<br />초기화될 수 있으므로 거부해야 합니다.</li>
<li>FIFO를 쓰기 전용으로 열면 reader가 없는 경우 작업이 무기한 대기할 수<br />있습니다.</li>
<li><code>ftruncate()</code>를 정규 파일이 아닌 객체에 호출했을 때의 동작은 플랫폼마다<br />다를 수 있습니다.</li>
<li>Android content URI와 외부 파일 시스템은 로컬 POSIX 경로가 아니므로 기존<br />storage backend를 계속 사용해야 합니다.</li>
<li>파일 시스템 작업으로 UI 및 브라우저 메인 시퀀스가 블로킹되어서는 안<br />됩니다.</li>
</ul>
<h2 id="해결-내용">해결 내용</h2><h3 id="1-posix-로컬-파일-전용-생성-함수-추가">1. POSIX 로컬 파일 전용 생성 함수 추가</h3><p><code>content/browser/file_system_access/file_system_access_manager_impl.cc</code>에<br />POSIX이면서 Android가 아닌 플랫폼을 위한<br /><code>CreateAndTruncateLocalFile()</code>을 추가했습니다.</p>
<p>새 파일을 열 때 기본 모드로 <code>0666</code>을 전달해 최종 권한을 프로세스의 umask가<br />결정하도록 했습니다.</p>
<p>핵심 흐름을 단순화하면 다음과 같습니다.</p>
<pre><code class="hljs language-cpp"><span class="hljs-function">base::ScopedFD <span class="hljs-title">fd</span><span class="hljs-params">(HANDLE_EINTR(open(
    path.value().c_str(),
    O_CREAT | O_WRONLY | O_NONBLOCK | O_CLOEXEC | O_NOFOLLOW,
    <span class="hljs-number">0666</span>)))</span></span>;

<span class="hljs-keyword">if</span> (!fd.<span class="hljs-built_in">is_valid</span>()) {
  <span class="hljs-keyword">return</span> <span class="hljs-literal">false</span>;
}

<span class="hljs-keyword">struct</span> <span class="hljs-title class_">stat</span> file_info;
<span class="hljs-keyword">if</span> (<span class="hljs-built_in">HANDLE_EINTR</span>(<span class="hljs-built_in">fstat</span>(fd.<span class="hljs-built_in">get</span>(), &amp;file_info)) != <span class="hljs-number">0</span> ||
    !<span class="hljs-built_in">S_ISREG</span>(file_info.st_mode)) {
  <span class="hljs-keyword">return</span> <span class="hljs-literal">false</span>;
}

<span class="hljs-keyword">return</span> base::<span class="hljs-built_in">File</span>(std::<span class="hljs-built_in">move</span>(fd)).<span class="hljs-built_in">SetLength</span>(<span class="hljs-number">0</span>);</code></pre><p>각 플래그는 다음 목적을 가집니다.</p>
<ul>
<li><code>O_CREAT</code>: 대상이 존재하지 않으면 새 파일을 생성합니다.</li>
<li><code>O_WRONLY</code>: 파일을 초기화할 수 있도록 쓰기 전용으로 엽니다.</li>
<li><code>O_NONBLOCK</code>: reader가 없는 FIFO 같은 특수 파일을 열다가 작업이 멈추는<br />것을 방지합니다.</li>
<li><code>O_CLOEXEC</code>: 생성한 파일 디스크립터가 자식 프로세스로 상속되지 않도록<br />합니다.</li>
<li><code>O_NOFOLLOW</code>: 선택된 최종 경로가 심볼릭 링크라면 링크를 따라가지 않고<br />실패시킵니다.</li>
<li><code>0666</code>: 실행 비트를 제외한 읽기·쓰기 권한을 기본값으로 제공하고 실제<br />권한은 umask가 제한하도록 합니다.</li>
</ul>
<p><code>open()</code> 단계에서는 의도적으로 <code>O_TRUNC</code>를 사용하지 않았습니다. 파일 타입을<br />확인하기 전에 내용을 지우지 않기 위해서입니다.</p>
<p>파일을 연 후에는 경로를 다시 검사하는 대신 동일한 파일 디스크립터에<br /><code>fstat()</code>을 호출합니다. 이를 통해 열린 객체가 정규 파일인지 확인하고,<br /><code>S_ISREG()</code>를 통과한 경우에만 <code>SetLength(0)</code>으로 내용을 비웁니다. 심볼릭<br />링크나 FIFO를 비롯한 비정규 파일은 파일 내용이 변경되기 전에 거부됩니다.</p>
<p>또한 <code>HANDLE_EINTR</code>로 인터럽트된 시스템 호출을 안전하게 재시도하고,<br /><code>base::ScopedFD</code>를 사용해 모든 반환 경로에서 디스크립터가 자동으로<br />정리되도록 했습니다.</p>
<h3 id="2-블로킹-파일-작업을-sequenced-file-task-runner로-분리">2. 블로킹 파일 작업을 sequenced file task runner로 분리</h3><p>POSIX <code>open()</code>, <code>fstat()</code>, truncate 작업은 파일 시스템 상태에 따라 블로킹될<br />수 있습니다. 따라서 해당 작업을 현재 시퀀스에서 직접 실행하지 않고 다음<br />경로로 전달했습니다.</p>
<pre><code class="hljs language-cpp"><span class="hljs-built_in">context</span>()-&gt;<span class="hljs-built_in">default_file_task_runner</span>()-&gt;<span class="hljs-built_in">PostTaskAndReplyWithResult</span>(
    FROM_HERE,
    base::<span class="hljs-built_in">BindOnce</span>(&amp;CreateAndTruncateLocalFile, fs_url.<span class="hljs-built_in">path</span>()),
    std::<span class="hljs-built_in">move</span>(did_create_and_truncate));</code></pre><p>파일 작업은 기존 sequenced file task runner에서 실행되며, 완료 결과만 원래<br />시퀀스로 전달됩니다. helper 내부에도 <code>base::ScopedBlockingCall</code>과<br /><code>BlockingType::MAY_BLOCK</code>을 선언해 블로킹 가능성을 명시했습니다.</p>
<p>비동기 작업이 진행되는 동안 <code>FileSystemAccessManagerImpl</code>이 파괴될 가능성에<br />대비해 완료 콜백은 <code>weak_factory_.GetWeakPtr()</code>를 사용하도록 구성했습니다.</p>
<h3 id="3-적용-범위를-로컬-posix-파일로-제한">3. 적용 범위를 로컬 POSIX 파일로 제한</h3><p>새 경로는 다음 조건을 모두 만족할 때만 사용합니다.</p>
<pre><code class="hljs language-cpp"><span class="hljs-built_in">BUILDFLAG</span>(IS_POSIX) &amp;&amp;
!<span class="hljs-built_in">BUILDFLAG</span>(IS_ANDROID) &amp;&amp;
entries.<span class="hljs-built_in">front</span>().type == PathType::kLocal</code></pre><p>따라서 다음 경로의 기존 동작은 변경하지 않았습니다.</p>
<ul>
<li>Android content URI</li>
<li>외부 또는 가상 파일 시스템</li>
<li>POSIX 로컬 파일이 아닌 storage backend 경로</li>
<li>Windows 등 비 POSIX 플랫폼</li>
</ul>
<p>이렇게 플랫폼과 저장소 유형별 책임을 분리해, 로컬 파일 권한 문제를<br />수정하면서 다른 backend의 동작이 함께 바뀌는 것을 방지했습니다.</p>
<h3 id="4-주요-코드-변경-규모">4. 주요 코드 변경 규모</h3><p><a href="https://chromium.googlesource.com/chromium/src/+/82ae2deac4cfe69f70538c876eddc62711ca01a3">최종 Chromium 커밋</a>은<br />두 파일을 수정했습니다.</p>
<ul>
<li><code>file_system_access_manager_impl.cc</code>: 48줄 추가, 4줄 삭제</li>
<li><code>file_system_chooser_browsertest.cc</code>: 177줄 추가, 6줄 삭제</li>
<li>합계: 225줄 추가, 10줄 삭제</li>
</ul>
<p>최종 커밋 위치는 <code>refs/heads/main@{#1687775}</code>입니다.</p>
<h2 id="테스트-방법">테스트 방법</h2><p>실제 umask, 심볼릭 링크, FIFO와 같은 운영체제 동작을 확인해야 하므로 새<br />검증은 단위 테스트보다 <code>IN_PROC_BROWSER_TEST</code> 기반 브라우저 통합 테스트에<br />집중했습니다.</p>
<h3 id="1-새-파일이-umask를-반영하는지-검증">1. 새 파일이 umask를 반영하는지 검증</h3><p>기존 <code>SaveFile</code> 테스트에서 RAII 방식의 <code>ScopedUmaskSetter</code>를 사용해 테스트<br />중 umask를 <code>0002</code>로 설정했습니다.</p>
<pre><code class="hljs language-text">open() 생성 모드: 0666
umask:            0002
기대 권한:         0664</code></pre><p><code>showSaveFilePicker()</code>가 완료된 직후 <code>GetPosixFilePermissions()</code>로 실제 권한이<br /><code>0664</code>인지 확인했습니다. <code>ScopedUmaskSetter</code>의 소멸자는 기존 umask를<br />복원하므로 이후 테스트에 영향을 남기지 않습니다.</p>
<h3 id="2-기존-파일-권한-보존-및-내용-초기화-검증">2. 기존 파일 권한 보존 및 내용 초기화 검증</h3><p><code>SaveFile_TruncatesExistingFile</code> 테스트에서는 기존 파일의 권한을 <code>0620</code>으로<br />설정한 후 저장 대상으로 선택했습니다.</p>
<p>다음 두 조건을 함께 확인했습니다.</p>
<ul>
<li>기존 파일의 내용이 정상적으로 비워집니다.</li>
<li>기존 권한 <code>0620</code>이 변경되지 않습니다.</li>
</ul>
<p>이를 통해 새 파일에만 <code>0666 &amp; ~umask</code>가 적용되고, 기존 파일에는 <code>chmod</code>와<br />같은 권한 변경이 발생하지 않음을 검증했습니다.</p>
<h3 id="3-심볼릭-링크-거부-검증">3. 심볼릭 링크 거부 검증</h3><p><code>SaveFile_RejectsSymbolicLink</code> 테스트를 추가했습니다.</p>
<ul>
<li>실제 대상 파일과 그 파일을 가리키는 심볼릭 링크를 생성합니다.</li>
<li>심볼릭 링크를 저장 대상으로 반환합니다.</li>
<li><code>showSaveFilePicker()</code> Promise가 거부되는지 확인합니다.</li>
<li>실제 대상 파일의 내용이 변경되지 않았는지 다시 읽어 검증합니다.</li>
</ul>
<p>이 테스트는 <code>O_NOFOLLOW</code>가 링크 대상을 보호하고 있음을 확인합니다.</p>
<h3 id="4-fifo-안전성-검증">4. FIFO 안전성 검증</h3><p>FIFO에 대해서는 서로 다른 두 상황을 테스트했습니다.</p>
<ul>
<li><code>SaveFile_RejectsFifo</code>: reader를 미리 열어 write-only <code>open()</code>이 성공하게<br />만든 후, <code>fstat()</code>과 <code>S_ISREG()</code> 검사에서 FIFO가 거부되는지 확인합니다.</li>
<li><code>SaveFile_RejectsFifoWithoutReader</code>: reader가 없는 FIFO를 선택해<br /><code>O_NONBLOCK</code> 덕분에 작업이 대기하지 않고 즉시 실패하는지 확인합니다.</li>
</ul>
<p>첫 번째 테스트는 정규 파일 타입 검사를, 두 번째 테스트는 비동기 작업의<br />무한 대기 방지를 각각 검증합니다.</p>
<h3 id="5-외부-파일-시스템-회귀-검증">5. 외부 파일 시스템 회귀 검증</h3><p><code>SaveFile_ExternalPathUsesStorageBackend</code> 테스트에서는 외부 가상 경로를 저장<br />대상으로 전달했습니다.</p>
<p>테스트 중 umask를 <code>0022</code>로 설정했지만 생성된 파일 권한이 기존 backend<br />동작인 <code>0600</code>인지 확인했습니다. 이를 통해 새 POSIX 로컬 경로가 외부 파일<br />시스템 처리까지 가로채지 않는다는 것을 검증했습니다.</p>
<h3 id="6-기존-관찰자-테스트-및-cq-검증">6. 기존 관찰자 테스트 및 CQ 검증</h3><p>커밋의 테스트 메타데이터에는 다음 필터가 명시되었습니다.</p>
<pre><code class="hljs language-text">FileSystemChooserBrowserTest.SaveFile_*
FileSystemAccessObserverBrowserTest.WritableReports*</code></pre><p>Gerrit Patch Set 9는 LUCI CQ dry run을 통과했고, Rahul Singh과 Ming-Ying<br />Chung의 <code>Code-Review+1</code>을 받은 뒤 full CQ를 거쳐 2026년 8월 28일 <code>main</code>에<br />병합되었습니다.</p>
<p>별도의 성능 벤치마크는 수행하지 않았습니다. 이번 변경은 저장 대화상자에서<br />파일을 생성하거나 초기화할 때 한 번 실행되는 경로이며, 파일 작업은 기존<br />sequenced file task runner에서 처리됩니다. 다만 저장 지연에 대한 정량적인<br />성능 수치는 이 CL의 검증 범위에 포함되지 않았습니다.</p>
<h2 id="배운-점">배운 점</h2><ul>
<li>POSIX 파일 생성 권한은 <code>open()</code>에 전달한 mode만으로 결정되지 않고<br /><code>mode &amp; ~umask</code>로 결정됩니다.</li>
<li>테스트 값의 선택도 중요합니다. umask <code>0022</code> → <code>0644</code>만 검사하면 구현이<br />잘못해서 처음부터 <code>0644</code>를 전달해도 통과할 수 있습니다. 리뷰 과정에서<br />umask <code>0002</code> → <code>0664</code>로 변경해 기본 생성 모드가 실제로 <code>0666</code>인지까지<br />검증했습니다.</li>
<li>umask는 프로세스 전역 상태이므로 테스트에서는 적용 구간을 최소화하고<br />RAII로 반드시 원래 값으로 복원해야 합니다.</li>
<li>경로를 먼저 검사하고 나중에 다시 여는 방식은 검사와 사용 사이에 파일이<br />바뀔 수 있습니다. 열린 디스크립터에 <code>fstat()</code>을 적용하면 실제로 사용할<br />객체 자체를 검증할 수 있습니다.</li>
<li><code>O_TRUNC</code>를 <code>open()</code>과 함께 사용하면 파일 타입을 확인하기 전에 데이터가<br />변경될 수 있습니다. 먼저 안전하게 연 뒤 정규 파일임을 확인하고<br />truncate하는 순서가 중요합니다.</li>
<li><code>O_NONBLOCK</code>은 FIFO처럼 <code>open()</code> 자체가 대기할 수 있는 파일에 대한 방어<br />수단이며, <code>S_ISREG()</code> 검사는 <code>open()</code>에 성공한 특수 파일까지 거부하는<br />별도의 방어 계층입니다.</li>
<li>로컬 파일, Android content URI, 외부 파일 시스템은 같은 저장 API를<br />사용하더라도 서로 다른 backend 의미를 가질 수 있으므로 수정 범위를<br />명확히 제한해야 합니다.</li>
<li>리뷰 의견을 통해 테스트 assertion을 <code>showSaveFilePicker()</code> 직후로<br />옮겼습니다. 검증하려는 동작과 assertion을 가까이 배치하면 이후의<br /><code>createWritable()</code> 동작과 혼동하지 않고 실패 원인을 파악할 수 있습니다.</li>
<li>향후 유사한 POSIX 로컬 파일 생성 경로가 추가된다면 이번 helper의 공통화<br />여부를 검토할 수 있습니다. 또한 다른 특수 파일 타입과 플랫폼별 오류<br />변환에 대한 회귀 테스트도 확장할 수 있습니다.</li>
</ul>
