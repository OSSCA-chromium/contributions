1a:T39fe,<p>Linux의 POSIX/C locale에서 OPFS의 비 ASCII 디렉터리 이름이 손실되어 자식 핸들이 부모 디렉터리를 가리키거나, 디렉터리 열거 결과의 이름이 비어 버리던 문제를 수정했습니다. 자식 URL 생성부터 디렉터리 열거까지 OPFS 이름이 보존되도록 개선했습니다.</p>
<h2 id="문제-설명">문제 설명</h2><p>비개발자 관점에서는 웹 애플리케이션이 <code>"テスト用の本"</code> 같은 이름으로 폴더를 만들었을 때, 성공한 것처럼 보이지만 실제로는 부모 폴더를 돌려줄 수 있는 문제였습니다. 이 상태에서 파일을 쓰면 예상한 하위 폴더가 아니라 부모 폴더에 저장될 수 있었습니다.</p>
<p>기술적으로는 <code>content/browser/file_system_access</code>의 OPFS 경로 처리 문제였습니다. OPFS의 가상 경로 component가 process locale에 의존하는 네이티브 경로 변환을 거치면서 손실됐습니다. 최종 변경에서는 OPFS 자식 URL과 열거 결과의 이름 모두 storage path representation을 보존하도록 했습니다.</p>
<p>Origin은 웹 페이지를 구분하는 보안·스토리지 경계이며, OPFS(Origin Private File System)는 각 origin에 제공되는 브라우저 내부 전용 파일시스템입니다. 사용자의 로컬 파일시스템과 달리 OPFS 경로는 sandboxed virtual filesystem의 논리적 component입니다.</p>
<p>이 File System Access 경로에서 OPFS URL은 <code>storage::kFileSystemTypeTemporary</code>로 표현됩니다. 기존 <code>GetChildURL()</code>은 OPFS를 포함한 non-Android filesystem 이름을 다음과 같이 처리했습니다.</p>
<pre><code class="hljs language-cpp">parent.<span class="hljs-built_in">virtual_path</span>().<span class="hljs-built_in">Append</span>(
    base::FilePath::<span class="hljs-built_in">FromUTF8Unsafe</span>(basename));</code></pre><p><code>FromUTF8Unsafe()</code>는 <code>SYSTEM_NATIVE_UTF8</code>이 아닌 POSIX 환경에서 UTF-8 문자열을 현재 locale의 native multibyte encoding으로 변환합니다. C locale은 일본어 같은 문자를 표현하지 못하므로 변환 결과에서 이름이 손실될 수 있었습니다.</p>
<pre><code class="hljs language-text">OPFS child name
→ locale-dependent native conversion
→ C locale에서 non-ASCII 이름 손실
→ parent.virtual_path().Append("")
→ child path == parent path
→ child URL이 parent URL과 alias</code></pre><p>이름의 안전성 검사는 변환 전에 통과하므로 API 호출은 오류 없이 성공할 수 있습니다. 이슈의 재현 결과에서는 반환된 핸들의 이름은 요청값처럼 보였지만 <code>isSameEntry(parent)</code>가 <code>true</code>였고, 하위 디렉터리에 쓰려던 파일이 부모 디렉터리에 생성됐습니다. UTF-8 locale과 ASCII 이름에서는 정상적으로 동작했습니다.</p>
<h3 id="root-cause">Root Cause</h3><p>문제는 서로 다른 경로 의미론을 동일한 변환으로 처리한 데 있었습니다.</p>
<ul>
<li>OPFS는 sandboxed virtual path component의 storage representation을 사용합니다.</li>
<li>local/external 등 다른 filesystem type은 기존 native path 변환 동작을 유지해야 합니다.</li>
<li>Android는 content URI를 포함한 별도의 path-construction 분기를 사용하므로 이번 변경 대상이 아닙니다.</li>
</ul>
<p>따라서 모든 filesystem 이름을 일괄적으로 바꾸지 않고, OPFS에 해당하는 temporary filesystem 분기만 storage 변환 helper를 사용하도록 범위를 제한했습니다.</p>
<h2 id="해결-내용">해결 내용</h2><h3 id="자식-url의-경로-보존">자식 URL의 경로 보존</h3><p><code>GetChildURL()</code>에서 OPFS 이름은 <code>storage::StringToFilePath()</code>로 변환해 가상 경로에 추가하도록 변경했습니다.</p>
<pre><code class="hljs language-cpp">base::FilePath child_path =
    parent.<span class="hljs-built_in">type</span>() == storage::kFileSystemTypeTemporary
        ? parent.<span class="hljs-built_in">virtual_path</span>().<span class="hljs-built_in">Append</span>(
              storage::<span class="hljs-built_in">StringToFilePath</span>(basename))
        : parent.<span class="hljs-built_in">virtual_path</span>().<span class="hljs-built_in">Append</span>(
              base::FilePath::<span class="hljs-built_in">FromUTF8Unsafe</span>(basename));</code></pre><p><code>StringToFilePath()</code>는 POSIX에서 문자열 바이트를 그대로 <code>FilePath</code>에 보존하므로 locale-dependent conversion을 거치지 않습니다. 다른 filesystem type의 기존 변환과 Android의 별도 분기는 유지했습니다.</p>
<p>초기 패치에서는 <code>AppendUTF8()</code>을 사용했지만, 리뷰에서 모든 <code>GetChildURL()</code> call site가 해당 함수의 UTF-8 precondition을 보장하는지 질문이 제기됐습니다. 디렉터리 열거 경로의 basename은 <code>FilePathToString()</code>에서 유래하므로, storage 경로의 왕복 표현을 위한 <code>StringToFilePath()</code>가 더 적절하다고 판단했습니다.</p>
<h3 id="디렉터리-열거-이름-보존">디렉터리 열거 이름 보존</h3><p>리뷰어가 요청한 열거 테스트를 작성하면서 두 번째 locale-dependent conversion 지점도 발견했습니다. OPFS 열거 경로에서는 별도의 <code>display_name</code>이 제공되지 않아 <code>CreateEntry()</code>가 <code>basename.AsUTF8Unsafe()</code>로 fallback했고, C locale에서는 반환되는 <code>entry-&gt;name</code>이 빈 문자열이 될 수 있었습니다.</p>
<p>OPFS에 한해 반대 방향의 storage helper를 사용하도록 수정했습니다.</p>
<pre><code class="hljs language-cpp">std::string name = display_name;
<span class="hljs-keyword">if</span> (name.<span class="hljs-built_in">empty</span>()) {
  name = url.<span class="hljs-built_in">type</span>() == storage::kFileSystemTypeTemporary
             ? storage::<span class="hljs-built_in">FilePathToString</span>(basename.<span class="hljs-built_in">path</span>())
             : basename.<span class="hljs-built_in">AsUTF8Unsafe</span>();
}</code></pre><p>최종 변경은 기존 implementation과 unittest 두 파일에만 한정했습니다. Mojo validation, <code>base::FilePath</code>, storage subsystem, Android 및 다른 filesystem type의 동작은 변경하지 않았습니다.</p>
<h2 id="테스트-방법">테스트 방법</h2><p>두 Linux 회귀 테스트는 다음 조건을 결합해 locale-dependent failure를 재현합니다.</p>
<pre><code class="hljs language-text">C locale + non-ASCII OPFS child
→ 기존 native conversion: FAIL
→ storage path representation 보존: PASS</code></pre><h3 id="getchildurl_nonasciinameinclocale">GetChildURL_NonAsciiNameInCLocale</h3><p><code>base::ScopedLocale("C")</code>에서 <code>"テスト用の本"</code>의 child URL을 직접 생성합니다. 기존 구현에서는 child path가 <code>"probe"</code>로 남아 parent와 같아졌지만, 수정 후에는 <code>"probe/テスト用の本"</code>이 보존됩니다.</p>
<h3 id="getentries_preservesnonasciiopfsname">GetEntries_PreservesNonAsciiOPFSName</h3><p>C++ <code>content_unittests</code>에서 실제 temporary filesystem root를 구성하고 다음 흐름을 실행합니다.</p>
<pre><code class="hljs language-text">GetDirectory(create=true)
→ GetEntries()
→ 반환된 entry의 type과 name 확인</code></pre><p>이는 renderer까지 포함하는 browser E2E 테스트는 아니지만, content와 storage 경로를 연결해 사용자에게 반환되는 결과까지 확인하는 통합형 회귀 단위 테스트입니다. 테스트 작성 과정에서 PS5 구현은 entry를 정상적으로 찾으면서도 이름을 <code>""</code>으로 반환한다는 사실을 확인했고, PS6의 <code>CreateEntry()</code> 수정으로 해결했습니다.</p>

<h2 id="배운-점">배운 점</h2><ul>
<li>같은 문자열이라도 filesystem abstraction에 따라 virtual component와 native path라는 서로 다른 의미를 가질 수 있습니다.</li>
<li>locale-dependent 문제는 <code>ScopedLocale("C")</code>처럼 재현 조건을 테스트 안에 고정해야 결정적으로 검증할 수 있습니다.</li>

<li>리뷰 질문은 문구 수정에 그치지 않고 숨은 API precondition과 미검증 경로를 발견하는 계기가 될 수 있습니다.</li>
<li>동일 원인의 문제는 보완하되 Mojo나 Unicode validation 정책까지 변경하지 않도록 CL 범위를 통제해야 합니다.</li>
</ul>
