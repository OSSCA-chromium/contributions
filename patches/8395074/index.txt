1a:T1cc4,<ul>
<li>문제: inotify 읽기 버퍼 끝에 남은 이동 이벤트가 다음 배치 처리 과정에서 누락될 수 있었습니다.</li>
<li>해결: 버퍼가 해제되기 전에 대기 중인 이동 이벤트를 전달하고, 읽기 경계를 제어하는 회귀 테스트를 추가했습니다.</li>
<li>결과: 다음 배치가 준비된 경우에도 이동 이벤트를 보존하며, 코드 리뷰와 CQ를 거쳐 Chromium에 반영되었습니다.</li>
</ul>
<h2 id="문제-설명">문제 설명</h2><p><code>FilePathWatcher</code>의 inotify reader는 <code>IN_MOVED_FROM</code>과 같은 cookie를 가진 <code>IN_MOVED_TO</code>를 같은 읽기 버퍼 안에서 만나면 하나의 이동으로 묶어 처리합니다. 버퍼 끝에서 짝을 찾지 못한 <code>IN_MOVED_FROM</code>은 현재 버퍼 내부를 가리키는 포인터로 잠시 보관합니다.</p>
<p>기존 구현은 <code>poll()</code>로 다음 배치가 즉시 준비되어 있는지 확인한 뒤, 다음 배치가 없을 때만 대기 중인 이벤트를 전달했습니다. 다음 배치가 준비되어 있으면 현재 버퍼가 해제되고 다음 반복에서 대기 포인터가 초기화되어, 이전 버퍼의 마지막 이동 이벤트가 조용히 사라질 수 있었습니다.</p>
<p>이 문제는 CQ 타임아웃을 조사하는 과정에서 발견했습니다. 다만 당시 CQ에서 실제로 어느 지점에 읽기 경계가 생겼는지는 확인되지 않았으므로, 해당 타임아웃의 원인으로 단정하지 않았습니다.</p>
<h2 id="해결-내용">해결 내용</h2><ol>
<li><p><strong>버퍼 해제 전 대기 이벤트 전달</strong></p>
<p><code>file_path_watcher_inotify.cc</code>에서 다음 배치 유무와 관계없이, 현재 버퍼가 유효한 동안 대기 중인 <code>IN_MOVED_FROM</code>을 전달하도록 수정했습니다. 기존 조건과 변경한 조건의 핵심 차이는 다음과 같습니다.</p>
<pre><code class="hljs language-diff"><span class="hljs-deletion">-if (!has_batch &amp;&amp; pending_move_from_event) {</span>
<span class="hljs-addition">+if (pending_move_from_event) {</span></code></pre><p>이동 이벤트를 묶는 범위는 같은 읽기 버퍼 안으로 유지했습니다. 서로 다른 버퍼로 나뉜 이동 이벤트는 cookie가 같아도 별도의 알림으로 전달합니다.</p>
</li>
<li><p><strong>실제 읽기 루프를 테스트에서 호출하도록 분리</strong></p>
<p>읽기와 이벤트 분류 로직을 <code>ReadInotifyEvents()</code>로 추출하고, 콜백으로 단일 이벤트 또는 이동 이벤트 쌍을 전달하도록 구성했습니다. <code>ThreadMain()</code>은 이 콜백을 기존 <code>InotifyReader</code> 처리 함수에 연결합니다.</p>
<p><code>file_path_watcher_inotify.h</code>에는 <code>ReadInotifyEventsForTesting()</code>을 선언하여 테스트에서도 같은 읽기 루프를 호출하도록 했습니다. 이벤트 포인터는 콜백 실행 중에만 유효하므로 버퍼 수명 밖으로 보관하지 않습니다.</p>
</li>
<li><p><strong>리뷰를 반영한 오류 처리 순서 유지</strong></p>
<p>리뷰에서는 대기 이벤트를 전달하는 위치가 <code>poll()</code> 오류 경로의 동작을 바꾸는지 확인했습니다. Patch Set 4에서 이벤트 전달을 <code>poll_result &lt; 0</code> 검사 뒤로 옮겨, 오류가 발생하면 기존처럼 즉시 반환하도록 했습니다. 정상적인 <code>poll_result == 0</code>과 <code>poll_result &gt; 0</code> 경로에서는 모두 대기 이벤트를 전달합니다.</p>
</li>
</ol>
<h2 id="테스트-방법">테스트 방법</h2><p><code>file_path_watcher_unittest.cc</code>에 Linux와 ChromeOS용 <code>InotifyReaderTest</code>를 추가했습니다. <code>socketpair(AF_UNIX, SOCK_SEQPACKET, ...)</code>로 배치를 미리 큐에 넣어, 파일 시스템이나 스레드 실행 시점에 의존하지 않고 읽기 경계와 다음 배치의 준비 상태를 재현합니다. 테스트는 <code>ReadInotifyEventsForTesting()</code>을 통해 실제 읽기 루프를 실행합니다.</p>

<p>Gerrit 기록상 Patch Set 4는 2026년 9월 16일 UTC에 CQ dry run을 통과했습니다. 이후 full run에서 <code>win-arm64-compile-dbg</code>의 WebUI 헤더 의존성 검사 실패가 기록되었으며, 재실행 후 9월 21일 23:57 UTC(한국 시간 9월 22일 08:57)에 최종 병합되었습니다.</p>
<p>최종 커밋은 <code>2591a644d878a7c24c69cceb6ef3b06646892b8f</code>이며, 커밋 위치는 <code>refs/heads/main@{#1702219}</code>입니다. 위 테스트와 CQ 결과는 패치 및 Gerrit 기록을 기준으로 정리했으며, 보고서 작성 과정에서 Chromium 테스트를 별도로 실행하지는 않았습니다.</p>
<h2 id="배운-점">배운 점</h2><ul>
<li>버퍼 내부를 가리키는 포인터로 이벤트를 보관할 때는 다음 반복으로 넘어가기 전에 버퍼 수명과 미처리 이벤트를 함께 확인해야 합니다.</li>
<li>읽기 경계가 원인인 문제는 패킷 소켓으로 경계를 고정하면 실행 타이밍에 의존하지 않는 회귀 테스트로 재현할 수 있습니다.</li>
<li>이벤트 누락을 수정할 때도 기존의 이동 이벤트 결합 범위와 오류 처리 순서를 유지해야 합니다.</li>
<li>조사 중 발견한 결함과 최초 장애의 원인은 구분해야 하며, 재현되지 않은 인과관계는 커밋 설명에서 단정하지 않아야 합니다.</li>
</ul>
