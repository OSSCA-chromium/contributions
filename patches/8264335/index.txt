<p>기존 동작이 이미 <code>TypeError</code> 였으므로 <strong>assert 는 런타임 동작을 바꾸지 않고 오류 메시지만 명확하게 합니다.</strong> 반면 옵셔널 체이닝은 "절대 <code>undefined</code> 면 안 되는 값"에 쓰면 프로토콜 계약 위반을 조용히 삼켜 원인 파악을 어렵게 만듭니다.</p>
<p>키가 항상 존재한다는 근거는 같은 파일에서 확인할 수 있었습니다.</p>
<ul>
<li><code>enable()</code> 이 <code>this.events.set(...)</code> 을 먼저 호출하고 그 뒤에 <code>startObserving()</code> 을 호출합니다. 이벤트가 도착하는 시점에는 항상 키가 존재합니다.</li>
<li>이 맵에서 키를 삭제하는 코드가 없습니다.</li>
</ul>
<p><code>assertNotNullOrUndefined</code> 는 DevTools 프로덕션 코드 여러 곳에서 쓰이는 관례이며, <code>ui/legacy/Treeoutline.ts</code> 가 같은 형태로 사용합니다.</p>
<h2 id="테스트-방법">테스트 방법</h2><pre><code class="hljs language-bash">npm run build
npm run lint -- --lint-only front_end/panels/application/BackgroundServiceModel.ts</code></pre><ul>
<li>DevTools 는 <code>autoninja</code> 가 아니라 npm 스크립트로 빌드합니다. <code>npm run build</code> 가 타입 검사를 포함하므로, 억제문을 제거한 뒤에도 타입 오류가 없음을 확인했습니다.</li>
<li><code>npm run lint</code> 는 로컬 기본값이 <strong>자동 수정 ON</strong> 이라 파일을 조용히 고치고 통과할 수 있습니다. 봇과 같은 조건(캐시 OFF, 자동 수정 OFF)으로 검증하려면 <code>--lint-only</code> 를 붙여야 하고, 실행 후 <code>git status</code> 로 파일이 변경되지 않았는지 확인해야 합니다.</li>
<li>패치셋 2에서 CQ dry run 을 통과했습니다.</li>
<li>런타임 동작 변화는 없습니다. 전제가 지켜지는 정상 경로에서는 동일하게 동작하고, 위반 시에만 오류 메시지가 명확해집니다.</li>
</ul>
<h2 id="배운-점">배운 점</h2><ul>
<li><p><strong>CQ 실패 요약문은 원인이 아니라 실패한 스텝의 이름입니다.</strong> 이 CL 의 dry run 이 <code>Failure in Lint Check</code> 로 실패했지만, 빌드 로그를 7단계 내려가 보니 실제 원인은 봇에서 <code>third_party/depot_tools/vpython3</code> 를 찾지 못한 것이었고 ESLint 는 시작조차 하지 못한 상태였습니다. <strong>같은 봇의 다른 CL 두 건이 동일한 지점에서 실패한 것</strong>이 인프라 문제라는 결정적 근거가 되었습니다. 내 코드가 남의 CL 빌드를 깨뜨릴 방법은 없기 때문입니다. 이 근거를 코멘트로 정리해 남기자 리뷰어가 바로 상황을 확인해 주었습니다.</p>
</li>
<li><p><strong>외부 기여자는 <code>Code-Review+1</code> 이 두 개 필요합니다.</strong> Gerrit 의 제출 조건식이 커미터에게는 한 개, 그 외에는 두 개를 요구합니다. 최근 머지된 외부 기여자 CL 을 확인해 보면 대부분 처음부터 리뷰어를 2~3명 지정합니다. 한 명만 넣고 기다리면 정체됩니다.</p>
</li>
<li><p><strong>리뷰어가 배정을 다른 사람에게 넘기면 그 판단을 존중해야 합니다.</strong> 처음 지정한 리뷰어가 스스로를 제거하고 다른 담당자를 넣었는데, 이를 원래대로 되돌렸다가 반나절 넘게 리뷰가 진행되지 않았습니다. 넘긴 쪽에서는 이미 처리를 마친 CL 이라 다시 볼 이유가 없었던 것입니다. 리뷰어가 바뀌었을 때는 <strong>누가 바꿨는지</strong>를 먼저 확인해야 합니다.</p>
</li>
<li><p><strong><code>git config diff.ignoreSubmodules all</code> 이 필요합니다.</strong> <code>build</code> 와 <code>third_party/depot_tools</code> 는 실제 git 서브모듈인데 gclient 가 기록된 리비전보다 새 커밋으로 체크아웃해 두어 항상 diff 가 남고, presubmit 의 <code>CheckNoUncheckedFiles</code> 가 이를 잡아 업로드를 막습니다. <code>git checkout -- build</code> 로는 인덱스만 되돌아가 즉시 재발하므로 설정을 바꿔야 합니다. 기본값은 depot_tools 가 넣어둔 <code>dirty</code> 이며, 커밋 포인터 차이까지 무시하려면 <code>all</code> 이 필요합니다.</p>
</li>
</ul>
