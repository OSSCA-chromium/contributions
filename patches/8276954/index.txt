1a:T58d9,<p>Chromium Blink의 <code>FormData</code>가 <code>Blob</code>과 이름이 변경된 <code>File</code>을 조회할 때마다<br />새로운 <code>File</code> 객체를 만들던 동작을 수정했습니다. 값을 entry에 추가하는<br />시점에 한 번만 <code>File</code>로 정규화하여 <code>get()</code>, <code>getAll()</code>, iterator가 동일한<br />객체를 반환하게 하고, multipart 직렬화에 필요한 파일 메타데이터도<br />보존했습니다.</p>
<h2 id="문제-설명">문제 설명</h2><p><a href="https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#create-an-entry">HTML Standard의 create-an-entry 알고리즘</a>은<br /><code>FormData</code> entry를 생성할 때 <code>Blob</code>과 <code>File</code> 값을 다음과 같이 처리합니다.</p>
<ol>
<li>값이 <code>File</code>이 아닌 <code>Blob</code>이면 같은 바이트를 나타내고 이름이 <code>"blob"</code>인<br />새 <code>File</code>을 만듭니다.</li>
<li><code>filename</code>이 주어졌다면 같은 바이트를 나타내고 해당 이름을 가진 새<br /><code>File</code>을 만듭니다.</li>
<li>정규화된 값을 entry의 value로 저장합니다.</li>
</ol>
<p><a href="https://xhr.spec.whatwg.org/#interface-formdata">XMLHttpRequest Standard의 FormData 알고리즘</a>은<br /><code>append()</code>와 <code>set()</code>이 이 create-an-entry 알고리즘으로 entry를 만든다고<br />규정합니다. 이후 <code>get()</code>, <code>getAll()</code>, iterator는 entry list에 이미 저장된<br />value를 반환합니다.</p>
<p>그러나 기존 Blink 구현은 생성 시점에 값을 정규화하지 않았습니다.<br /><code>FormData::Entry</code>는 <code>Member&lt;Blob&gt; blob_</code>과 별도의 <code>filename_</code>을 저장하고,<br /><code>GetFile()</code>이 호출될 때마다 다음 변환을 수행했습니다.</p>
<ul>
<li>일반 <code>Blob</code>이면 이름이 <code>"blob"</code> 또는 지정된 filename인 <code>File</code>을 새로<br />생성했습니다.</li>
<li>기존 <code>File</code>에 filename override가 있으면 <code>File::Clone()</code>으로 매번 새<br />객체를 만들었습니다.</li>
<li>filename override가 없는 기존 <code>File</code>만 원래 객체를 그대로 반환했습니다.</li>
</ul>
<p>따라서 다음과 같이 같은 entry를 반복해서 조회해도 서로 다른 객체가<br />반환됐습니다.</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">const</span> data = <span class="hljs-keyword">new</span> <span class="hljs-title class_">FormData</span>();
data.<span class="hljs-title function_">set</span>(<span class="hljs-string">"blob"</span>, <span class="hljs-keyword">new</span> <span class="hljs-title class_">Blob</span>());

data.<span class="hljs-title function_">get</span>(<span class="hljs-string">"blob"</span>) === <span class="hljs-title class_">Array</span>.<span class="hljs-title function_">from</span>(data)[<span class="hljs-number">0</span>][<span class="hljs-number">1</span>]; <span class="hljs-comment">// false</span></code></pre><p>일반 <code>Blob</code>을 <code>File</code>로 바꿀 때 <code>base::Time::Now()</code>를 사용했기 때문에 새<br />객체뿐 아니라 합성된 <code>lastModified</code> 값도 조회 시점마다 달라질 수 있었습니다.<br />이는 같은 entry의 저장된 value를 반환해야 하는 명세의 데이터 모델과 맞지<br />않았으며, Window와 Worker에서 실행되는 WPT가 모두 실패하는 원인이었습니다.</p>
<p>수정할 때는 객체 identity만 맞추는 것으로 충분하지 않았습니다.</p>
<ul>
<li>filename을 생략한 경우와 명시적으로 빈 문자열을 전달한 경우를 구분해야<br />합니다.</li>
<li>filename override가 없는 기존 <code>File</code>은 원래 객체 identity를 유지해야<br />합니다.</li>
<li>filename override가 있는 기존 <code>File</code>은 한 번만 clone하면서 backing file<br />경로, 상대 경로, Blob data handle, 수정 시간을 보존해야 합니다.</li>
<li>multipart 직렬화에서 <code>webkitRelativePath</code>, 명시적 filename override,<br />MIME type, backing file 경로를 기존과 동일하게 처리해야 합니다.</li>
</ul>

  <span class="hljs-built_in">DCHECK</span>(file_);
  <span class="hljs-keyword">return</span> file_.<span class="hljs-built_in">Get</span>();
}</code></pre><p><code>File</code>은 <code>Blob</code>의 하위 타입이므로 기존 Blob 기반 호출 경로를 유지하기 위해<br /><code>GetBlob()</code>도 남겼습니다. 다만 실제 entry 내부에는 이미 정규화된 <code>File</code>이<br />저장됩니다.</p>
<h3 id="3-filename의-null과-빈-문자열을-구분">3. filename의 null과 빈 문자열을 구분</h3><p>리뷰에서는 <code>filename.IsNull()</code>이 빈 문자열과 다른 동작을 만드는 점이<br />논의됐습니다. 이 차이는 의도된 동작입니다.</p>
<ul>
<li>null <code>String</code>: JavaScript 호출에서 filename 인수가 생략됐음을 나타냅니다.</li>
<li>빈 <code>String</code>: 개발자가 filename으로 <code>""</code>을 명시했음을 나타냅니다.</li>
</ul>
<p>filename이 생략된 기존 <code>File</code>은 원래 객체와 이름을 유지합니다. 반면 빈<br />filename이 명시되면 빈 이름을 가진 <code>File</code>을 한 번 clone합니다. 단순히<br /><code>filename.empty()</code>로 검사하면 이 두 API 입력을 구분할 수 없으므로 기존의<br /><code>IsNull()</code> 의미를 유지했습니다.</p>
<h3 id="4-backing-file-메타데이터와-multipart-동작-보존">4. backing file 메타데이터와 multipart 동작 보존</h3><p><code>third_party/blink/renderer/core/html/forms/form_data.cc</code>의<br /><code>EncodeMultiPartFormData()</code>도 정규화된 <code>File</code>을 직접 사용하도록<br />정리했습니다.</p>
<pre><code class="hljs language-cpp">File* file = entry-&gt;<span class="hljs-built_in">isFile</span>() ? entry-&gt;<span class="hljs-built_in">GetFile</span>() : <span class="hljs-literal">nullptr</span>;</code></pre><p>multipart header와 body를 만드는 기존 의미는 유지했습니다.</p>
<ul>
<li><code>webkitRelativePath()</code>가 있으면 상대 경로를 filename으로 사용합니다.</li>
<li><code>append()</code> 또는 <code>set()</code>에 filename을 명시했다면 그 값이 최종적으로<br />우선합니다.</li>
<li>파일의 MIME type이 비어 있으면 <code>application/octet-stream</code>을 사용합니다.</li>
<li>backing file의 경로가 있으면 경로와 <code>LastModifiedTime()</code>을 encoded file<br />element에 전달합니다.</li>
<li>메모리 기반 파일이면 동일한 Blob data handle을 append합니다.</li>
</ul>
<p><code>File::Clone(filename)</code>이 단순히 바이트만 복사하지 않는지도 단위 테스트로<br />확인했습니다. 이름이 바뀐 clone은 원래 파일과 다른 객체이지만 다음 정보는<br />그대로 유지됩니다.</p>
<ul>
<li>backing file 경로</li>
<li><code>webkitRelativePath</code></li>
<li>Blob data handle</li>
<li><code>LastModifiedTime()</code></li>
</ul>
<p>entry에는 <code>filename_</code>도 계속 보관합니다. 이를 통해 정규화 시점이 바뀌어도<br />multipart 직렬화에서 명시적 filename override가 상대 경로보다 우선하는<br />기존 동작을 유지합니다.</p>

<h2 id="테스트-방법">테스트 방법</h2><h3 id="1-blob-entry-단위-테스트">1. Blob entry 단위 테스트</h3><p><code>BlobEntryCreatesFileOnce</code> 테스트를<br /><code>third_party/blink/renderer/core/html/forms/form_data_test.cc</code>에<br />추가했습니다.</p>
<p>이 테스트는 일반 <code>Blob</code>을 append한 뒤 다음을 확인합니다.</p>
<ul>
<li>저장된 값이 기본 이름 <code>"blob"</code>을 가진 <code>File</code>인지</li>
<li>원래 Blob과 동일한 Blob data handle을 사용하는지</li>
<li><code>Entries()[0]-&gt;GetFile()</code>을 반복해도 같은 포인터인지</li>
<li><code>get()</code>과 <code>getAll()</code>도 같은 <code>File</code> 포인터를 반환하는지</li>
</ul>
<h3 id="2-filename-override와-backing-file-단위-테스트">2. filename override와 backing file 단위 테스트</h3><p>같은 파일에 추가한 <code>FileEntryWithFilenameIsClonedOnce</code> 테스트는 backing<br />file을 나타내는 <code>File</code>에 <code>"renamed.txt"</code> filename override를 적용합니다.</p>
<p>다음 조건을 함께 검증합니다.</p>
<ul>
<li>원래 <code>File</code>과 clone은 서로 다른 객체입니다.</li>
<li>clone의 이름은 <code>"renamed.txt"</code>입니다.</li>
<li>backing file 경로 <code>/tmp/form_data_test</code>가 유지됩니다.</li>
<li><code>webkitRelativePath</code> 값 <code>relative/original.txt</code>가 유지됩니다.</li>
<li>Blob data handle과 수정 시간이 보존됩니다.</li>
<li>multipart header의 filename은 <code>"renamed.txt"</code>입니다.</li>
<li>encoded body는 Blob이 아니라 backing file element를 사용합니다.</li>
<li>entry를 다시 조회해도 같은 clone을 반환합니다.</li>
</ul>
<h3 id="3-wpt-file-identity-검증-확대">3. WPT File identity 검증 확대</h3><p><code>third_party/blink/web_tests/external/wpt/xhr/formdata/set-blob.any.js</code>에<br /><code>assert_file_identity()</code> helper를 추가했습니다.</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">function</span> <span class="hljs-title function_">assert_file_identity</span>(<span class="hljs-params">formData, name, expected</span>) {
  <span class="hljs-title function_">assert_equals</span>(formData.<span class="hljs-title function_">get</span>(name), expected);
  <span class="hljs-title function_">assert_equals</span>(formData.<span class="hljs-title function_">getAll</span>(name)[<span class="hljs-number">0</span>], expected);
  <span class="hljs-keyword">const</span> entry = <span class="hljs-title class_">Array</span>.<span class="hljs-title function_">from</span>(formData)
      .<span class="hljs-title function_">find</span>(<span class="hljs-function">(<span class="hljs-params">[entryName]</span>) =&gt;</span> entryName === name);
  <span class="hljs-title function_">assert_equals</span>(entry[<span class="hljs-number">1</span>], expected);
}</code></pre><p>이 helper를 사용해 다음 경우를 검증합니다.</p>
<ul>
<li><code>set()</code>에 일반 Blob과 기본 filename을 사용한 경우</li>
<li><code>set()</code>에 일반 Blob과 custom filename을 사용한 경우</li>
<li><code>set()</code>에 File을 filename override 없이 사용한 경우</li>
<li><code>set()</code>에 File과 custom filename을 사용한 경우</li>
<li><code>append()</code>에 일반 Blob을 사용한 경우</li>
<li><code>append()</code>에 일반 Blob과 custom filename을 사용한 경우</li>
</ul>
<p>기존 WPT는 Blob 기본 이름, type, <code>lastModified</code>도 계속 검사합니다. 변경 후<br />Window와 Worker의 기존 failure expectation이 필요 없어져 두 expected 파일을<br />삭제했습니다.</p>
<p>커밋 메시지에는 <code>xhr/formdata</code> WPT 27개를 실행했다고 기록했습니다. Blink<br />WPT 변경은 Chromium의 자동 export 과정을 통해<br /><a href="https://github.com/web-platform-tests/wpt/pull/62284">web-platform-tests/wpt PR #62284</a>로도<br />전달됐습니다.</p>

<h2 id="배운-점">배운 점</h2><ul>
<li>표준 알고리즘은 최종 값의 타입뿐 아니라 변환이 일어나는 시점까지<br />규정할 수 있습니다. create-an-entry에서 값을 한 번 정규화해야 이후 조회<br />API가 같은 entry value를 반환할 수 있습니다.</li>
<li>같은 바이트와 메타데이터를 가진 두 <code>File</code>도 JavaScript에서는 서로 다른<br />객체입니다. 웹 API의 객체 identity는 <code>===</code>로 관찰할 수 있는 호환성<br />요구사항입니다.</li>
<li>조회 함수 안에서 <code>base::Time::Now()</code>를 사용해 객체를 합성하면 호출할<br />때마다 <code>lastModified</code> 같은 관찰 가능한 값이 달라질 수 있습니다.</li>
<li>optional string에서는 null과 빈 문자열이 서로 다른 API 입력을 나타낼 수<br />있습니다. <code>IsNull()</code>을 <code>empty()</code>로 단순화하면 filename 생략과 빈 filename<br />지정을 구분하지 못합니다.</li>
<li>객체 생성 시점을 옮길 때는 조회 경로만 보지 않고 multipart 직렬화처럼<br />같은 내부 표현을 소비하는 경로도 함께 확인해야 합니다.</li>
<li>이름을 바꾸기 위해 <code>File</code>을 clone하더라도 backing file 경로, 상대 경로,<br />Blob handle, 수정 시간처럼 직렬화에 필요한 메타데이터를 보존해야 합니다.</li>
<li>구현 단위 테스트는 내부 포인터와 backing metadata를 검증하고, WPT는<br />JavaScript에서 관찰되는 identity를 검증합니다. 두 계층을 함께 사용하면<br />내부 표현과 웹 표준 동작을 모두 보호할 수 있습니다.</li>
<li>WPT가 통과한 뒤 기존 expected failure 파일을 제거해야 실제 회귀가 다시<br />발생했을 때 테스트 실패를 숨기지 않습니다.</li>
<li>Chromium의 <code>external/wpt</code> 변경은 Blink W3C Test Autoroller가 upstream WPT<br />PR로 export하므로 Chromium 내부 수정과 웹 플랫폼 공통 테스트의 흐름을<br />함께 확인할 수 있습니다.</li>
</ul>
