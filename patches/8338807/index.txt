1a:T2a49,<p>IndexedDB의 LevelDB 백엔드에서 레코드 버전을 트랜잭션별로 캐시해,<br />연속 쓰기 중 메타데이터 조회가 유발하는 flush를 줄이는 변경을 제안했습니다.<br />리뷰에서 해당 백엔드가 deprecated 상태여서 비핵심 개선을 받지 않는다는<br />방침을 확인했고, 이를 수용해 2026년 9월 2일 CL을 중단했습니다.<br />이번 기여에서는 구현 내용과 함께, 리뷰를 통해 배운 작업 대상 선정 기준을<br />중심으로 정리합니다.</p>
<h2 id="문제-설명">문제 설명</h2><p><a href="https://chromium-review.googlesource.com/c/chromium/src/+/8338807/2">CL 설명</a>은<br /><code>PutRecord()</code>마다 <code>LAST_VERSION</code>을 읽으면서 대기 중인 LevelDB 쓰기와<br />undo log를 flush하는 문제를 다룹니다. 관련 이슈는 커밋 메시지에 연결된<br /><a href="https://issues.chromium.org/issues/41460075">Chromium Issue 41460075</a>입니다.</p>
<p>기존 <code>GetNewVersionNumber()</code>는 레코드를 쓸 때마다 object store의 마지막<br />버전을 <code>GetInt()</code>로 읽고, 1을 더한 값을 다시 기록했습니다.<br />이 읽기가 사용하는<br /><a href="https://chromium.googlesource.com/chromium/src/+/f3601a9e090fb4f78823e87afe02f626cfa7f9a8/components/services/storage/indexed_db/transactional_leveldb/transactional_leveldb_transaction.cc#67"><code>TransactionalLevelDBTransaction::Get()</code></a>은<br />실제 조회 전에 <code>WriteChangesAndUndoLog()</code>를 호출합니다. 따라서 같은<br />트랜잭션에서 레코드를 연속으로 써도 버전 조회 때문에 이전 쓰기를 반복해서<br />내보낼 수 있었습니다.</p>
<p>이 내부 flush와 트랜잭션의 논리적 커밋은 서로 다른 단계입니다. 이번 CL은<br />버전 조회로 발생하는 불필요한 내부 쓰기를 줄이려는 최적화였습니다.</p>
<h2 id="해결-내용">해결 내용</h2><h3 id="1-트랜잭션별-버전-캐시-제안">1. 트랜잭션별 버전 캐시 제안</h3><p>병합되지 않은 최종 Patch Set 2에는 다음 변경을 구현했습니다.</p>
<ol>
<li><code>BackingStore::Transaction</code>에 object store ID와 마지막 버전을 저장하는<br /><code>object_store_last_version_numbers_</code> 맵을 추가했습니다.</li>
<li><code>GetNewVersionNumber()</code>를 트랜잭션의 private 메서드로 옮겼습니다.<br />캐시에 값이 없을 때만 기존 메타데이터를 읽고, 이후에는 캐시에서 버전을<br />가져오도록 했습니다.</li>
<li>새 버전은 기존처럼 <code>PutInt()</code>로 기록하되, 기록 요청이 성공한 뒤 캐시도<br />갱신했습니다. 반복적인 메타데이터 읽기를 생략해 쓰기를 버퍼에 유지하려는<br />접근입니다.</li>
<li>같은 트랜잭션에서 새 object store를 만들면 초기 버전인 <code>1</code>을 캐시에<br />넣었습니다. 첫 레코드를 쓸 때도 이미 알고 있는 초기값을 다시 읽지 않게<br />했습니다.</li>
<li>공용 LevelDB operations 파일에서 기존 helper의 선언과 구현을 제거하고,<br /><code>PutRecord()</code>가 새 메서드를 호출하도록 바꿨습니다.</li>
</ol>
<p>변경은 <code>content/browser/indexed_db/instance/leveldb/</code> 아래의 구현·헤더·테스트<br />5개 파일에 한정되며, 총 83줄 추가와 48줄 삭제입니다. Patch Set 2는<br />커밋 메시지를 수정한 것으로, Patch Set 1과 코드 변경은 동일합니다.</p>
<h3 id="2-핵심-리뷰-deprecated-백엔드의-변경-수용-범위">2. 핵심 리뷰: deprecated 백엔드의 변경 수용 범위</h3><p>2026년 9월 2일 Evan Stade는<br /><a href="https://chromium-review.googlesource.com/c/chromium/src/+/8338807/comments/aface897_0094e526">Patch Set 2의 리뷰 코멘트</a>에서<br />다음과 같이 설명했습니다.</p>
<blockquote>
<p>we are not really accepting non-critical improvements for IndexedDB's LevelDB backend as it's deprecated.</p>
</blockquote>
<p>IndexedDB의 LevelDB 백엔드가 deprecated 상태이므로, 그 백엔드에 대한<br />비핵심 개선은 받지 않는다는 의미입니다. 이 코멘트는 작업 대상의 유지보수<br />단계와 변경의 필요성을 먼저 확인하게 했습니다.</p>
<p>이번 제안은 레코드 버전 조회를 줄이는 최적화였고, 리뷰어는 이 백엔드에서<br />그러한 개선을 받아들이는 범위가 제한되어 있음을 알려줬습니다. 공개된<br />리뷰에는 캐시 구현의 특정 결함이나 테스트 실패를 지적한 내용은 없습니다.<br />따라서 중단 사유는 <strong>deprecated 백엔드에 대한 비핵심 개선이라는 점</strong>으로<br />기록하는 것이 정확합니다.</p>
<p>이 피드백을 통해, 구현 가능한 개선점을 찾은 다음에는 해당 코드가 현재도<br />적극적으로 개선하는 대상인지 확인해야 한다는 점을 배웠습니다. 오래된<br />이슈와 수정 가능한 코드가 남아 있다는 사실만으로 현재의 기여 우선순위까지<br />알 수는 없습니다. 작업을 시작하기 전에 최근 리뷰와 담당자의 방침을<br />확인해야 합니다.</p>
<p>또한 코멘트의 범위는 IndexedDB의 LevelDB 백엔드에 대한 <strong>non-critical<br />improvements</strong>입니다. 긴급한 수정까지 모두 거절한다는 뜻으로 확대해서<br />해석할 수는 없으며, 이 코멘트만으로 예외가 되는 변경의 구체적인 기준까지<br />확정할 수도 없습니다.</p>
<h3 id="3-대응-cl-중단과-다음-이슈-선택-기준-정리">3. 대응: CL 중단과 다음 이슈 선택 기준 정리</h3><p>리뷰를 확인한 뒤 CL을 <code>abandoned</code>로 변경했습니다.<br /><a href="https://chromium-review.googlesource.com/c/chromium/src/+/8338807/comments/e2f7af70_5c82f409">후속 답변</a>에서는<br />이미 CL을 중단했음을 알리고, 앞으로 IndexedDB 이슈를 선택할 때 이 방침을<br />고려해 deprecated LevelDB 백엔드의 비핵심 작업을 피하겠다고 답했습니다.</p>

<h2 id="테스트-방법">테스트 방법</h2><p>패치에는 <code>leveldb_backing_store_unittest.cc</code>의<br /><code>LevelDbBackingStoreTest.PutRecordsDoNotFlushBeforeCommit</code> 테스트를<br />추가했습니다. 테스트가 검증하도록 작성된 내용은 다음과 같습니다.</p>
<ol>
<li>데이터베이스와 object store를 만들고 read-write 트랜잭션을 시작합니다.</li>
<li>같은 object store에 <code>PutRecord()</code>로 레코드 두 개를 씁니다.</li>
<li>트랜잭션을 커밋하기 전에 하위 데이터베이스에서 <code>LAST_VERSION</code>을 직접<br />읽어, 저장된 값이 초기 버전 <code>1</code>인지 확인합니다.</li>
<li>트랜잭션을 커밋한 뒤 다시 읽어 최종 버전이 <code>3</code>인지 확인합니다.</li>
</ol>
<p>이 테스트의 검증 범위는 위 연속 쓰기 시나리오의 커밋 전후 메타데이터<br />값입니다. 성능 향상률은 측정하지 않습니다.</p>
<p>공개된 CL 설명과 메시지에는 로컬 테스트 실행 결과, CQ 통과 기록,<br />성능 측정치가 없어 통과 여부나 개선 수치를 확인할 수 없습니다.<br />이 기록에서는 패치에 추가된 테스트의 검증 내용까지만 설명합니다.</p>
<h2 id="배운-점">배운 점</h2><ul>
<li><strong>이슈를 고를 때 백엔드의 유지보수 상태부터 확인해야 합니다.</strong> 동일한<br />IndexedDB 영역이라도 작업 대상 구현의 deprecated 여부에 따라 변경을<br />받아들이는 기준이 달라질 수 있습니다.</li>
<li><strong>최적화의 구현 가능성과 프로젝트의 우선순위를 함께 판단해야 합니다.</strong><br />불필요한 읽기를 줄일 수 있다는 근거에 더해, 현재 그 백엔드에 변경을<br />추가할 필요가 있는지도 확인해야 합니다.</li>
<li><strong>짧은 리뷰에서도 적용 범위를 정확히 읽어야 합니다.</strong> 이번 코멘트는<br />deprecated LevelDB 백엔드의 비핵심 개선에 관한 방침이었습니다.<br />구현이 틀렸다는 평가나 IndexedDB 전체에 대한 방침으로 일반화하지 않고,<br />실제로 언급된 범위에 맞춰 대응했습니다.</li>
<li><strong>중단 이유와 후속 행동을 함께 남기면 다음 작업에 활용할 수 있습니다.</strong><br /><code>abandoned</code> 상태와 함께 이유를 기록하고, 이후 이슈 선택에서 같은 종류의<br />작업을 피하겠다는 구체적인 방향을 답변에 남겼습니다.</li>
<li><strong>저장소의 읽기가 쓰기를 유발할 수 있습니다.</strong> 트랜잭션 내부의<br />메타데이터 조회가 버퍼와 undo log를 flush하므로, 반복 조회를 최적화할<br />때는 하위 저장 계층의 동작까지 확인해야 합니다.</li>
</ul>
