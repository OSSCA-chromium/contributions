<h2 id="문제-설명">문제 설명</h2><ul>
<li><p>issue url: <a href="https://crbug.com/40176243">https://crbug.com/40176243</a> (Time) · <a href="https://crbug.com/40251269">https://crbug.com/40251269</a> (TimeDelta)</p>

<li><p><code>sql::Statement</code>는 시간 컬럼을 읽고 쓰는 전용 접근자를 제공하고, <strong>헤더가 직접 "이 스니펫들을 대체하라"고 지시</strong>합니다:</p>
<blockquote>
<p>[sql/statement.h] This is equivalent to the following snippets, which should be replaced.<br /><code>base::Time::FromInternalValue(ColumnInt64(col))</code> /<br /><code>base::Time::FromDeltaSinceWindowsEpoch(base::Microseconds(ColumnInt64(col)))</code><br />TODO(crbug.com/40176243): Migrate all time serialization to this method, and then remove the migration details above.</p>
</blockquote>
</li>
<li><p>2026년 1월 <a href="https://crrev.com/c/7455767">CL 7455767</a>이 이 마이그레이션의 쓰기 쪽 일부를 이행하고 <code>Fixed:</code>로 두 이슈를 닫았습니다. 그런데 <strong>이슈 제목 자체가 "Migrate to <code>BindTime()</code> and <code>ColumnTime()</code>"</strong> 으로 읽기까지 범위였고, 읽기 쪽과 여러 줄에 걸친 쓰기 패턴은 그대로 남았습니다. 헤더의 TODO 두 개도 ToT에 살아 있습니다.</p>
</li>
<li><p>그래서 history 컴포넌트 안에서 <strong>읽기와 쓰기가 비대칭</strong>인 상태가 됐습니다. 같은 컬럼을 한쪽에서는 접근자로 쓰고 다른 쪽에서는 손으로 변환해 읽습니다.</p>
<ul>

<li><code>keyword_search_term.cc:29</code> — <code>last_visit_time</code>을 <code>url_database.cc</code>는 <code>BindTime()</code>으로 쓰고, 여기서는 손으로 읽음</li>
<li><code>visit_annotations_database.cc</code> — 같은 파일 900행은 <code>BindTime()</code>인데 330·333·412·415행은 <code>BindInt64(N, delta.InMicroseconds())</code></li>

<h2 id="해결-내용">해결 내용</h2><p>세 가지 패턴을 각각 대응하는 접근자로 바꿨습니다. 총 10곳 / 3파일, +14/−18.</p>
<pre><code class="hljs language-cpp"><span class="hljs-comment">// 읽기 (base::Time) — DownloadDatabase::QueryDownloads(), KeywordSearchTermVisitFromStatement()</span>

<p><strong>변환은 바이트 단위로 동일합니다.</strong> <code>base::Time</code>의 internal value가 곧 Windows epoch 기준 마이크로초이고, <code>ColumnTime()</code>은 <code>FromDeltaSinceWindowsEpoch(Microseconds(int64))</code>로 정확히 그것을 복원합니다(<code>sql/statement.cc</code>). <code>ColumnTimeDelta()</code>는 <code>Microseconds(int64)</code>, <code>BindTimeDelta()</code>는 <code>InMicroseconds()</code>입니다. 저장 포맷·스키마·마이그레이션은 그대로입니다.</p>
<p><code>Fixed:</code>가 아닌 <code>Bug: 40176243, 40251269</code>를 썼습니다. 남은 22곳이 다른 컴포넌트에 있고, 헤더의 TODO는 시리즈 마지막 CL에서 지울 예정입니다.</p>

<h2 id="배운-점">배운 점</h2><ul>
<li><strong><code>Fixed</code>로 닫힌 이슈가 끝난 이슈는 아닙니다.</strong> 여기서는 이슈 제목이 이행되지 않은 범위(<code>ColumnTime()</code>)를 그대로 담고 있었고 헤더의 TODO도 살아 있었습니다. 닫힌 번호를 <code>Bug:</code>로 참조하는 것은 허용되므로, 재오픈을 기다리며 멈추는 대신 CL 설명에 선례 CL을 part 1로 인용하고 남은 범위를 적었습니다.</li>
<li><strong>정규식 한 줄로 훑은 마이그레이션은 대개 여러 줄 패턴을 놓칩니다.</strong> 선례 CL이 남긴 9곳이 전부 인자가 줄바꿈된 형태였습니다. 남은 작업을 셀 때는 포매터가 어떻게 줄을 나눴을지까지 감안해 다시 스캔하는 편이 정확합니다.</li>
<li><strong>리팩토링의 범위는 코드량이 아니라 OWNERS 경계로 정합니다.</strong> 32곳을 한 번에 올리면 diff는 작아도 승인 여덟 개를 모아야 합니다. 컴포넌트 단위로 쪼개면 각 CL이 리뷰어 한 명으로 끝납니다.</li>
<li><strong>"동일하다"는 주장은 구현으로 확인해야 합니다.</strong> <code>FromInternalValue</code>와 <code>ColumnTime()</code>이 같다는 것을 문서가 아니라 <code>sql/statement.cc</code>의 실제 코드로 확인했고, 그 근거를 CL 설명에 적었습니다. 저장 포맷을 건드리는 것처럼 보이는 변경일수록 리뷰어가 가장 먼저 확인하고 싶어 하는 지점입니다.</li>
</ul>
