1a:T23a6,<p>특정 <code>StorageKey</code>의 사이트 데이터를 삭제할 때 남아 있던 Session Storage를 선택적으로 삭제하도록 Chromium의 DOM Storage 정리 로직을 수정했습니다.</p>
<h2 id="문제-설명">문제 설명</h2><p><code>StoragePartition::ClearData()</code>에 구체적인 <code>StorageKey</code>와 <code>REMOVE_DATA_MASK_LOCAL_STORAGE</code>를 전달하면 Local Storage는 삭제되지만 Session Storage는 삭제되지 않았습니다.</p>
<p>기존 구현은 구체적인 <code>StorageKey</code>가 지정된 경우 Session Storage 삭제를 명시적으로 건너뛰고 있었습니다.</p>
<pre><code class="hljs language-cpp"><span class="hljs-comment">// ClearDataImpl cannot clear session storage data when a particular origin</span>
<span class="hljs-comment">// is specified. Therefore we ignore clearing session storage in this case.</span>
<span class="hljs-comment">// TODO(lazyboy): Fix.</span>
<span class="hljs-keyword">if</span> (storage_key_origin_empty) {
  <span class="hljs-built_in">ClearSessionStorage</span>(...);
}</code></pre><p>따라서 호출자는 사이트 데이터가 삭제됐다고 판단하지만, 같은 사이트의 Session Storage가 남을 수 있었습니다.</p>
<p>Session Storage는 namespace별로 관리되며, 동일한 origin도 top-level site, nonce 등의 partitioning 정보에 따라 서로 다른 <code>StorageKey</code>를 가질 수 있습니다. 단순한 origin 비교로 삭제하면 다른 파티션의 데이터까지 삭제할 수 있어 전체 <code>StorageKey</code>를 기준으로 선택해야 했습니다.</p>
<h2 id="해결-내용">해결 내용</h2><ol>
<li><p><code>REMOVE_DATA_MASK_LOCAL_STORAGE</code>가 요청되면 구체적인 <code>StorageKey</code>의 존재 여부와 관계없이 Session Storage 삭제를 실행하도록 변경했습니다.</p>
</li>
<li><p>기존의 <code>CreateGenericStorageKeyMatcher()</code>가 생성하는 matcher를 Session Storage 삭제 경로에 전달했습니다.</p>
<ul>
<li>구체적인 <code>StorageKey</code>: 전체 <code>StorageKey</code> 동등성 비교</li>
<li>null matcher: 모든 항목 일치</li>
<li>filter와 policy matcher: 두 조건을 모두 만족하는 항목만 일치</li>
</ul>
</li>
<li><p><code>OnSessionStorageUsageInfo()</code>가 일반적인 <code>StorageKeyMatcherFunction</code>을 사용하도록 변경하고, 일치하는 <code>StorageKey</code>와 namespace의 데이터만 삭제했습니다.</p>
<pre><code class="hljs language-cpp">base::ConcurrentClosures concurrent;
<span class="hljs-keyword">for</span> (<span class="hljs-type">const</span> SessionStorageUsageInfo&amp; info : infos) {
  <span class="hljs-keyword">if</span> (storage_key_matcher &amp;&amp;
      !storage_key_matcher.<span class="hljs-built_in">Run</span>(info.storage_key)) {
    <span class="hljs-keyword">continue</span>;
  }

  dom_storage_context-&gt;<span class="hljs-built_in">DeleteSessionStorage</span>(
      info, concurrent.<span class="hljs-built_in">CreateClosure</span>());
}
std::<span class="hljs-built_in">move</span>(concurrent).<span class="hljs-built_in">Done</span>(std::<span class="hljs-built_in">move</span>(done_callback));</code></pre></li>
<li><p>Local Storage 삭제 후 Session Storage 삭제를 항상 예약하도록 기존 조건을 제거했습니다.</p>
<pre><code class="hljs language-cpp"><span class="hljs-built_in">ClearLocalStorage</span>(
    base::<span class="hljs-built_in">WrapRefCounted</span>(dom_storage_context), storage_policy_ref,
    combined_storage_key_matcher, storage_key, perform_storage_cleanup,
    begin, end, ...);

    base::<span class="hljs-built_in">WrapRefCounted</span>(dom_storage_context), generic_filter,
    perform_storage_cleanup, ...);</code></pre></li>
<li><p>공개 API에서 <code>REMOVE_DATA_MASK_LOCAL_STORAGE</code>가 Local Storage와 Session Storage를 모두 포함한다는 점을 명시했습니다.</p>
<pre><code class="hljs language-cpp"><span class="hljs-comment">// Includes both local storage and session storage.</span>

</ol>
<h2 id="테스트-방법">테스트 방법</h2><p><code>DOMStorageBrowserTest</code>에 다음 브라우저 회귀 테스트를 추가했습니다.</p>
<ol>
<li><p><code>ClearDataForStorageKeyClearsSessionStorage</code></p>
<ul>
<li>대상 origin의 Local Storage와 Session Storage가 모두 삭제되는지 확인</li>
<li>다른 origin의 데이터가 유지되는지 확인</li>
</ul>
</li>
<li><p><code>ClearDataForStorageKeyUsesFullStorageKey</code></p>
<ul>
<li>같은 origin이지만 top-level site가 다른 두 <code>StorageKey</code> 생성</li>
<li>두 개의 Session Storage namespace에 데이터를 저장</li>
<li>대상 <code>StorageKey</code>만 모든 namespace에서 삭제되는지 확인</li>
<li>sibling <code>StorageKey</code>의 데이터가 유지되는지 확인</li>
</ul>
</li>
<li><p><code>ClearDataWithNullMatcherClearsAllSessionStorage</code></p>
<ul>
<li>null matcher가 모든 Session Storage를 삭제하는 기존 동작을 유지하는지 확인</li>
</ul>
</li>
<li><p><code>ClearDataCombinesSessionStorageFilterAndPolicy</code></p>
<ul>
<li>filter와 storage policy를 모두 만족하는 항목만 삭제되는지 확인</li>
<li>filter에서 제외된 항목과 policy에서 제외된 항목이 각각 유지되는지 확인</li>
</ul>
</li>
</ol>

<p>추가로 다음 검사를 수행했습니다.</p>

<h2 id="배운-점">배운 점</h2><ul>
<li><p>Chromium의 <code>StorageKey</code>는 origin뿐만 아니라 top-level site, nonce, ancestor-chain bit까지 포함해 저장소 파티션을 구분한다는 점을 배웠습니다.</p>
</li>
<li><p>Session Storage는 하나의 origin에 하나만 존재하는 것이 아니라 namespace와 <code>StorageKey</code>의 조합으로 관리된다는 점을 확인했습니다.</p>
</li>
<li><p>선택적 데이터 삭제에서는 대상 데이터가 삭제되는 것뿐 아니라, 동일 origin의 다른 파티션이 보존되는지도 함께 검증해야 한다는 점을 배웠습니다.</p>
</li>
<li><p>null matcher, 구체적인 키, filter와 policy의 조합 등 기존 호출 경로를 모두 보호하는 회귀 테스트의 중요성을 배웠습니다.</p>
</li>
<li><p>동작을 수정할 때 구현뿐 아니라 공개 API 주석도 실제 의미와 일치하도록 함께 갱신해야 한다는 점을 배웠습니다.</p>
</li>
<li><p>Storage Service에 bulk 삭제 API를 추가하면 열거 비용을 줄일 수 있지만, Mojo 인터페이스와 백엔드까지 변경 범위가 확장됩니다. 이번 CL에서는 correctness 수정과 회귀 테스트에 집중하고 구조적 최적화는 별도 작업으로 분리하는 것이 적절하다고 판단했습니다.</p>
</li>
</ul>
