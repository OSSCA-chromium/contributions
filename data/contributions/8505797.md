Cache API가 작업을 시작하다 동기 예외를 만나면 사용하지 않게 된 내부 Promise resolver를 분리하도록 수정했습니다. 이후 도착한 응답도 해당 resolver를 처리하지 않게 합니다.

## 문제 설명

`Cache::addAll()`은 fetch를 시작하기 전에 내부 resolver를 만듭니다. fetch가 `ExceptionState`를 설정하면 Web IDL 바인딩은 별도의 거절된 Promise를 반환하지만, 기존 내부 resolver는 pending 상태로 남아 GC 중 `ScriptPromiseResolverBase::Dispose` 검사를 실패시킬 수 있습니다.

## 해결 내용

1. 응답을 모으는 barrier에 `Detach()`를 추가해 처리를 중단하고, 보관하던 Blob 목록을 비우며 resolver를 분리합니다.
2. `AddAllImpl()`에서 fetch 호출 직후 동기 예외를 확인합니다. 예외가 있으면 barrier를 분리하고 `EmptyPromise()`를 반환하며, 정상일 때만 `.Then()`을 연결합니다.
3. `Cache::put()`이 응답 본문 로딩을 시작하다 내부 예외를 만나는 경로에도 같은 정리를 적용합니다.

## 테스트 방법

- `ScopedFetcherForTests`가 동기 `TypeError`를 던지도록 설정하는 기능을 추가합니다.
- `AddAllDetachesResolverWhenFetchThrows`는 예외와 빈 내부 Promise 반환을 확인한 뒤 강제로 GC를 실행해 resolver 정리 경로를 검증합니다.
- 새 회귀 테스트는 `addAll()`의 fetch 예외를 직접 재현합니다. `put()`의 내부 예외에는 같은 정리 처리가 적용되지만 별도의 새 테스트가 추가된 것은 아닙니다.

확인한 CQ 통과 기록은 Patch Set 1(2026-10-02 UTC)입니다. 현재 보고서가 다루는 Patch Set 2의 통과 결과는 확인되지 않았으므로 이전 결과와 구분합니다. 보고서 작성 과정에서 Chromium 테스트를 별도로 실행하지는 않았습니다.

## 배운 점

- Web IDL 바인딩이 JavaScript에 반환하는 Promise와 C++ 내부 resolver가 관리하는 Promise는 예외 경로에서 서로 달라질 수 있습니다.
- 조기 반환할 때 resolver의 수명과 나중에 도착할 비동기 응답까지 정리해야 GC 시점의 오류를 막을 수 있습니다.
