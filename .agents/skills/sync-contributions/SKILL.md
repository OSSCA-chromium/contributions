# Sync contributions

Work from the contributions repository root. Read `CLAUDE.md` and
`data/docs/contribution-record.md` for the current data contract and module
taxonomy. This workflow is for the maintainer's batch updates.

## Regular update

Run `npm run sync:contributions -- --dry-run`, then inspect
`.cache/contribution-sync/report.json`. The script fetches public Gerrit
and independent GitHub PR metadata. It preserves mentee authored bodies,
authors, initial classifications, search terms and reference links.

Apply the preview with `npm run sync:contributions`. Check the diff and
the report. The script sets a separate `finalized` flag after successfully
verifying a Merged record. Later regular runs skip it while its date,
status and source fingerprint remain unchanged. Abandoned records are
checked again because they can be restored.

## Force update and classification review

When the user requests force, rerun all records, including finalized ones:

```bash
npm run sync:contributions -- --force --dry-run
```

Use the report's source subject, project and changed files, the complete
Markdown records and the archive's distribution to review `module` and
`kind`. File paths alone are not enough: choose the area that owns the
changed behavior. Ignore incidental AUTHORS, common build files and
baselines when identifying the main area. Apply the current taxonomy in
`src/lib/module-taxonomy.json`. `kind` describes the change itself, not its
module; allowed kinds are fix, feature, refactor, test, docs and cleanup.

If the taxonomy retired or renamed an old module, force previews still
collect source context and mark it `needsClassification`. Supply valid
replacement decisions before applying; invalid legacy modules cannot be
written or finalized by an actual update.

Write only justified changes to
`.cache/contribution-sync/classifications.json`, keyed by record ID:

```json
{
  "8300812": { "module": "blink", "kind": "fix" }
}
```

The example illustrates the format; it is not an instruction to change
that record. An empty object means the review found no classification
changes. Include a short rationale for each actual change in the work
report. Review similar contributions consistently across the archive.

```bash
npm run sync:contributions -- --force --dry-run --classification-file .cache/contribution-sync/classifications.json
npm run sync:contributions -- --force --classification-file .cache/contribution-sync/classifications.json
```

The command applies these decisions and preserves the old module as a
search term when it changes. It never infers classification by itself.
If the user requests a proposed new grouping without updating Markdown,
keep that proposal separate and do not include it in the classification
input or modify contribution records for that grouping.

## Date and completion rules

- Gerrit `created` is the original review creation date. For Merged,
  `submitted` supplies `resolvedDate`; for Abandoned, use the last exact
  `autogenerated:gerrit:abandon` event. Dates are UTC `YYYY-MM-DD`.
- Independent GitHub PRs use `created_at`, `merged_at`, or `closed_at`
  for a PR closed without merging. Open reviews have no `resolvedDate`.
- `updated` is source activity, not the closure date. The maintenance
  state's `verifiedAt` records the batch check and is not a site date.
- Leave `template.md` unchanged. State lives in
  `data/maintenance/contribution-sync.json`, outside mentee frontmatter.
- Failed source lookups, missing exact dates or invalid classifications
  must not be treated as successful updates. Report the error; do not
  invent dates or set flags manually to bypass it.
- No credentials are required for public sources. If a rate limit or
  private source blocks access, follow the repository's collector policy.

Run the repository's prescribed validation before publishing. Keep script,
site wording and generated record/state changes in separate meaningful
commits or stacked PRs. Follow the user's current publishing instructions.
